# 图书馆值班管理系统（duty-schedule-website）

这是一个以 `data/schedule.json` 为核心数据源的值班展示与调班工具。  
当前项目主要实现了：

- 按日期查看值班安排（按楼层、时段展示）
- 管理员登录后手动交换/移动值班人员
- 本地保存改动与更换日志（`localStorage`）
- 通过 Python 脚本把 Excel 值班表转换并合并为 JSON

## 这个项目现在“实际在做什么”

从代码看，当前流程是：

1. 线下准备 Excel 值班表（项目根目录已有多份 `.xlsx`）。
2. 运行 Python 脚本把 Excel 转为 `data/schedule.json`。
3. 前端页面读取 JSON，按日期展示值班信息。
4. 管理员在页面上做“交换/移动”操作，改动保存在浏览器本地。

说明：你提到的“给一张图片识别后得到表格”这一步，在当前仓库里还没有 OCR/图片识别代码。  
也就是说，目前仓库内的正式输入是 Excel，不是图片。

## 排序逻辑（重点）

### 当前逻辑

- 数据结构以 `date -> entries[]` 存储，entry 主要字段为：
  - `floor`（二层/三层/四层）
  - `time`（如 `16:30-18:00`、`19:00-21:00`）
  - `name`
  - `slot`（部分脚本会写入，部分历史数据缺失）
- 前端加载后会在 `processScheduleData` 中按楼层重新分组，并按出现顺序重设 `slot=1/2`。
- 渲染时按每层 `slot 1`、`slot 2` 展示；管理员交换也是按 `date + floor + slot` 定位。

### 现状结论

当前“排序/定位”依赖两个因素：

1. JSON 中每层条目的原始顺序  
2. `slot` 推断规则（有时按列、有时按时间、有时前端重算）

这会导致规则分散，且在“单时段日”“特殊节假日”“历史修复数据”场景下容易出现排序与定位不一致。

## 项目结构（关键文件）

- `index.html` / `styles.css` / `script.js`：前端页面与交互
- `config.js`：管理员与缓存配置
- `github_sync.js`：GitHub 同步类（当前前端主流程未完整接入）
- `data/schedule.json`：主数据文件（页面读取来源）
- `correct_excel_to_json.py`：较完整的 Excel 转换与合并脚本（含 slot 修正）
- `validate_all_data.py` / `simple_validate.py`：数据验证脚本
- `fix_*.py` / `check_*.py`：历史问题修复与排查脚本

## 本地运行

### 1) 启动前端（静态页面）

建议使用本地静态服务器，不要直接双击 `index.html`：

```bash
python -m http.server 8080
```

然后访问：`http://localhost:8080`

### 2) 数据处理环境（Python）

```bash
pip install pandas openpyxl
```

常用命令：

```bash
# 重新解析并合并 Excel 到 data/schedule.json（会先备份）
python correct_excel_to_json.py

# 验证数据完整性与 slot 正确性
python validate_all_data.py
```

## 接下来要做什么（建议路线）

### 第一阶段：先把“排序规则”收口

1. 固化唯一规则来源：只允许后端/脚本层写 `slot`，前端不再覆盖重算。  
2. 统一排序函数：固定按 `floor -> slot -> time` 排序，所有脚本复用同一实现。  
3. 为特殊日期建立显式类型：普通日/周末/闭馆日，避免靠推断。  
4. 清理一次性修复脚本，保留一条官方数据流水线（`import -> normalize -> validate -> output`）。

### 第二阶段：补齐“自动排班”能力

1. 新增排班引擎模块（独立于 UI）：输入人员名单、约束、日期范围，输出排班表。  
2. 约束建议：轮换公平、同人最小间隔、不可值班日期、节假日策略。  
3. 输出统一写入 `schedule.json`，并附带可追溯的生成参数。

### 第三阶段：接入“图片识别 -> 表格”链路

1. 增加 OCR 预处理模块（图片矫正、表格结构识别、文本识别）。  
2. OCR 输出先落为中间格式（CSV/JSON），再进入现有 normalize 流程。  
3. 提供人工校对界面，确认后再写入正式排班数据。

### 第四阶段：从“本地存储”升级到“可协作”

1. 增加后端 API（或云函数）存储变更，解决多设备不同步。  
2. 增加角色权限（查看/编辑/审核）。  
3. 对更换日志做服务端持久化与审计。

## 可以继续改进的点（清单）

- 安全：默认管理员密码仍较弱，建议改为环境变量+首次初始化强制修改。
- 稳定性：统一日期与时段格式，避免脚本间格式漂移。
- 可维护性：拆分 `script.js`（数据层、渲染层、交互层分离）。
- 质量保障：增加自动化测试（尤其是 slot/排序/交换逻辑）。
- 同步能力：把 `github_sync.js` 完整接入主流程或下线该入口，避免“有按钮无闭环”。
